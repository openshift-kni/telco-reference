# Upgrade orchestration examples

Reference `ClusterGroupUpgrade` (CGU) CRs which orchestrate the upgrade policies
generated by `core-upgrade-policies.yaml`, `core-upgrade-precache.yaml` and
`core-upgrade-mcps.yaml`.

These CRs are applied to the hub cluster directly with `oc apply -f`. They are
deliberately **not** referenced from `configuration/kustomization.yaml`:
syncing a CGU through GitOps would start the upgrade as soon as Argo CD
reconciles it.

| File | Use |
|------|-----|
| `cgu-upgrade-precache.yaml` | Optional. Pre-pull release and OLM images in an earlier maintenance window. |
| `cgu-upgrade.yaml` | Single release upgrade of the control plane. |
| `cgu-upgrade-double-hop.yaml` | Two chained control plane upgrades with the workers held paused across both. |
| `cgu-upgrade-finish.yaml` | Two CGUs: release the worker MachineConfigPools and clean up the pre-cache CRs, then restore `maxUnavailable`. Required after either upgrade path. |

`cgu-upgrade.yaml` and `cgu-upgrade-double-hop.yaml` both define a CGU named
`core-upgrade-5-1`. **Use one or the other, never both** -- applying both files
collides on that name.

An upgrade may re-use install and configuration policies; the restore step
below does exactly that. Upgrade-only policies intentionally carry no
`ran.openshift.io/ztp-deploy-wave` annotation, so they are not picked up by the
CGU that TALM builds from the waved policies at install time, and run only when
one of the CGUs here enforces them.

`core-install-mcp-unpause-5-1` in `core-finish.yaml` is the reverse case. It
unpauses every worker MCP at once with `maxUnavailable: 100%`, which is only
safe because no workloads are running yet; its placement requires `ztp-done` to
not exist, so it is unbound by the time an upgrade runs and cannot be used
here. Upgrades roll through the pools one at a time with
`core-upgrade-workers-N` instead.

## Ordering

Ordering between CGUs is expressed with `blockingCRs`, so all of them can be
applied at once and TALM will sequence them.

Optional prestage, run in an earlier maintenance window:

```
core-upgrade-precache
```

Upgrade, sequenced by `blockingCRs`:

```
core-upgrade-5-0 ─▶ core-upgrade-5-1 ─▶ core-upgrade-finish ─▶ core-upgrade-restore-mcp
```

A single hop starts the chain at `core-upgrade-5-1`. That CGU carries the same
name in both `cgu-upgrade.yaml` and the final hop of
`cgu-upgrade-double-hop.yaml`, which is what lets `cgu-upgrade-finish.yaml`
block on one name regardless of the path taken. If you rename either, rename
both and update the `blockingCRs` in the finish CGU.

Within `core-upgrade-5-1`, `core-overlay-registry-5-1` (catalog source and
IDMS/ITMS for the current release) runs first, before anything is paused. In
the double hop it also runs in `core-upgrade-5-0` for the same reason --
completing the upgrade typically needs the final target's updated IDMS, not
an intermediate one -- see the comments in `cgu-upgrade-double-hop.yaml` and
`core-overlay.yaml`.

## Cluster labels

The CGUs select clusters by label. The labels match the placements in the
upgrade PolicyGenerators:

| Label | Selects |
|-------|---------|
| `common: core` | All core clusters. Set at install time, see `install/example-standard-clusterinstance.yaml`. |
| `version: "5.1"` | The current release's configuration policies, including `core-overlay-registry-5-1` in `core-overlay.yaml` and `core-custom-mcp-set-maxavailable-5-1` in `core-finish.yaml`. |
| `upgrade-precache: ""` | `core-upgrade-precache.yaml` policies. Version independent. |
| `upgrade-version-5-1: ""` | `core-upgrade-policies.yaml` policies for the 5.1 hop. |
| `upgrade-version-5-0: ""` | The same policies from the `release-5.0` branch, for the first hop of a double hop. |
| `upgrade-finish: ""` | `core-upgrade-mcps.yaml` policies and `core-upgrade-precache-cleanup-5-1`. Version independent. |

**Apply every label the upgrade will need before starting**, then let each
stage drop its label as it finishes:

```bash
oc label --overwrite managedcluster <cluster> \
  version=5.1 upgrade-precache= upgrade-version-5-1= upgrade-finish=
```

`version` must be moved to the target release up front, not after the upgrade.
It binds the current release's configuration policies so they are available at
any point during the upgrade; they are only applied if a CGU names them
explicitly.

Do not have a CGU add the next stage's label in its `afterCompletion` action.
The placement binding and the policies it creates take time to propagate, and
the following CGU can begin before its policies are bound to the cluster.

Pre-applying the labels is safe because each CGU names only the policies for
its own stage in `managedPolicies`, and the policy names are unique per
release. The other stages' policies are bound and `inform` from the start, but
nothing enforces them until their CGU runs.

## Double hop

A double hop moves the control plane through two releases while the workers
stay paused, so the worker nodes reboot once rather than twice. 5.0 and 5.1 are
not EUS/ELC releases, so `cgu-upgrade-double-hop.yaml` is not itself an EUS
upgrade -- it is the same pattern, and an EUS/ELC upgrade is this chain with an
EUS/ELC release at the end of it.

It needs both generations of upgrade policies on the hub at once -- the `-5-0`
policies come from the `release-5.0` branch of this repository and the `-5-1`
policies from this branch. Point a second Argo CD policies Application at
`release-5.0`, or apply that branch's PolicyGenerator output manually, before
starting the first hop.

That second Application must render **only** the previous release's upgrade
policy generator -- `core-upgrade-policies.yaml`, or `core-upgrade.yaml` on a
branch cut before that file was split out -- not its full `configuration/`
tree. The worker-release policies (`core-upgrade-workers-N`) are deliberately
not version-suffixed, the same on every release branch by design, so
rendering the previous branch's copy of those would collide with this
branch's in the same `ztp-core-policies` namespace.

Hop 1 uses `release-5.0`'s `core-upgrade-prep-5-0` unmodified for the control
plane steps, but also enforces this branch's `core-overlay-registry-5-1`
first, since completing the upgrade typically needs the final target's
updated IDMS rather than an intermediate one. See the note in
`cgu-upgrade-double-hop.yaml` for the rarer case where the workers genuinely
need different IDMS content between the two hops.

See the "Orchestrating upgrade" section of [../README.md](../README.md) for the
full procedure.
